Getting started

Development uses Serverpod's embedded PostgreSQL, so there is no database to install and no container to run. The first startup creates the data directory under .serverpod/development/pgdata and applies the migrations in the repository.

{{{startCode}}}

The server listens on 8080 for the API and 8082 for the web pages. In development, the web server also answers on the API port.

Core concepts

Six objects carry the whole system. Understanding them is enough to read the API.

ConceptWhat it is
Workspace The tenant. Owns branding, restricted markets, the fraud policy, and demo mode. Every other record hangs off it.
Product A sellable item with SKU, category, packaging notes, shelf life, and safety instructions.
Batch A manufacturing run: reference, dates, quantity, and the distribution region used for leakage detection.
Identity One physical unit: QR token, HMAC signature, PIN hash, locked/recalled status, and first verification record.
Verification session One consumer scan being resolved, from token resolved through PIN prompted to a determined outcome.
Alert An escalation with severity, status, assignee, evidence, and the signals that produced it.

Endpoints and authentication

Calls are addressed as /<endpoint>/<method> with arguments in the JSON body. Authenticated calls carry a JWT as an Authorization: Bearer header. Public endpoints, such as the verification flow, need no token.

Authorization is always resolved server side from the caller's workspace membership. A workspace id sent by a client is checked against that membership and never trusted on its own.

Verification flow

This is the path a shopper takes. It is public, rate limited, and never reveals more than the outcome requires.

{{{curlVerifyCode}}}

Outcomes

  • authentic — the PIN matched and no risk rule escalated the scan
  • alreadyVerified — the token was already claimed, shown with the original time and place
  • invalidPin — the PIN did not match, with attempts counted and lockout tracked
  • highRisk — the scan matched signals that warrant an operator review
  • fraudSuspected — escalation was severe enough to short circuit the flow and open an alert
  • recalled — the unit or its batch is under an active recall

Replay protection keys off the token and the device fingerprint, so reloading the page resumes an existing session instead of burning a new identity claim.

Fraud signals

Eight checks are evaluated per scan against the workspace policy. The overall score is the highest severity seen, escalated to fraud suspected when a high severity signal is combined with any other.

SignalBase severityTrigger
Clone detectionHighThe same token resolved from locations too far apart to be one unit
Batch duplicationHighThe number of flagged units in a batch reaches the policy threshold
Velocity anomalyMediumScan count for one unit inside the window exceeds the threshold
PIN attackMediumFailed PIN attempts on one unit reach the policy threshold
Distributor leakageMediumThe scan country is outside the batch's distribution region
Grey marketMediumThe scan country is on the workspace restricted markets list
PIN lockoutMediumThe unit is temporarily locked after repeated wrong PINs
Offline backfillLowA field scan synced after the fact

Alerts are created according to policy: high risk alerts when the workspace asks for it, and fraud suspected always. The policy also decides whether the identity is locked automatically.

Offline sync

Field devices keep working without connectivity. A queued scan carries a local id, a device id, the token, the capture time, coarse location, and a provisional outcome produced on device.

StageWhere it runs
Scan captured, staged locallyDevice
Provisional verdict shownDevice
Records synced through Serverpod syncTransport
Scan converted into a real verification sessionRecurring job
Authoritative verdict available to the deviceServer

Queued consumer reports follow the same path, so a report filed in a dead zone still reaches triage.

Secrets

The server needs an HMAC signing key for QR tokens, a key for PIN encryption, and a key for webhook secrets. They live in config/passwords.yaml locally and as managed secrets in the cloud. The signing and encryption keys must not be rotated once data exists: rotating the signing key invalidates printed codes, and rotating the encryption key makes existing PINs unreadable.
